1. Mise en place Bitfocus Companion, module « Generic: HTTP Requests »

Chaque bouton de Companion envoie une requête à la régie, qui fait exactement ce que ferait le bouton de la Régie (un seul plein écran à la fois, une scène de fond masque les plein écran…). Choisis d'abord comment tu configures Companion : toutes les valeurs à copier sur cette page s'adaptent.

3. Boutons qui s'allument retours visuels

L'API ne prévient pas Companion d'un changement : Companion doit demander l'état régulièrement. Le plus simple passe par les adresses /value/…, qui répondent une seule valeur en texte brut (true, false, 2, brb…).

  1. Crée une variable personnalisée par information à suivre, par exemple kb_versus.
  2. Triggers → nouveau déclencheur, événement intervalle de temps (1 seconde par exemple), action GET de la connexion HTTP sur l'URL donnée par la route /value (ex. /value/overlays/versus), en enregistrant la réponse dans la variable (option de l'action GET qui stocke le résultat dans une variable personnalisée).
  3. Sur le bouton : feedback Internal → Variable: Check value, $(internal:custom_kb_versus) égal à true → fond rouge.

Score sur une touche : variables kb_scoreA / kb_scoreB alimentées par /value/match/scoreA et /value/match/scoreB, puis texte du bouton $(internal:custom_kb_scoreA) - $(internal:custom_kb_scoreB).

Une interrogation par seconde ne coûte rien à la régie. Évite de descendre sous 250 ms.

Référence · Généralités

  • Préfixe de toutes les routes : /valorant-tournament/api (les routes ci-dessous sont écrites sans).
  • Jeton obligatoire partout, au choix : en-tête Authorization: Bearer <jeton> (conseillé), en-tête X-Api-Key: <jeton>, paramètre ?key=<jeton> ou champ key du corps JSON.
  • Les actions sont des POST, les lectures des GET.
  • Paramètres des actions (kind, map, then, style, via, exclusive, fullscreen, stinger) : dans l'adresse (?kind=map) ou dans le corps JSON ({ "kind": "map" }) ; l'adresse l'emporte si les deux sont donnés. Ce qui fait partie du chemin (overlay, scène, emplacement, preset, équipe, plus / minus) reste dans l'URL.
  • Le corps est lu en JSON quel que soit son Content-Type (4 ko au plus) ; un corps qui n'est pas un objet JSON est ignoré. Un JSON mal formé envoyé en application/json est refusé par NodeCG lui-même (500, « Internal error »).
  • Un POST envoyé par une page web d'un autre site est refusé (403) ; Companion, curl et les scripts ne sont pas concernés.
  • Rien n'est mis en cache (Cache-Control: no-store). Chaque action réussie est notée dans le journal de la régie (Companion : …).

Réponse d'une action réussie (200) : { "ok": true, "done": "Versus affiché", "state": { … } } — done décrit ce qui a été fait, state est l'état complet après l'action (comme GET /state). Certaines routes ajoutent des champs, indiqués dans leur description.
Refus : { "ok": false, "error": "…" } avec le code ci-dessous.

CodeSignification
400Paramètre invalide (via, kind, then…)
401Jeton absent ou faux
403Requête envoyée par une page web d'un autre site
404Route, overlay, scène, emplacement, preset, map ou équipe inconnus
409Action impossible dans l'état actuel (rien à afficher, série terminée, aucune map gagnée à retirer, aucune map en cours…)
500Erreur interne (voir le journal de la régie), ou corps JSON mal formé (texte « Internal error »)
503Partie du serveur indisponible (erreur au démarrage, voir le journal)
